# OpenAI Responses compatibility evidence

Verified offline 2026-10-27, including the current Luna/Sol migration. The named, unselected opt-in model identifiers are recorded only in `config/llm_routes.yaml` (`tutor_openai`, `rubric_judge_openai`, `tutor_openai_sol`). All default tutor jobs and the default judge remain Anthropic. Both providers are registered for both roles; the named examples never select themselves. This is an offline compatibility profile, not evidence of account access or paid model quality. Live account/model compatibility remains unverified; see the [current migration handoff](2026-10-27-openai-current-models-handoff.md) for verification and remaining gates.

## SDK and native transport

The official Python SDK is pinned exactly to `openai==3.39.0` in the optional OpenAI extra and development extra. The [official release](https://github.com/openai/openai-python/releases/tag/v3.39.0) was published on 2026-10-26 at 19:14 UTC; PyPI's corresponding wheel was uploaded at 19:19 UTC. These public release/package endpoints were fetched before adding the dependency. The [official SDK documentation](https://developers.openai.com/api/docs/libraries) links the maintained Python package.

After installation, package metadata explicitly requires `httpx2<3,>=2.12.0`, and `openai/_base_client.py` imports `httpx2`. The scripted transport therefore uses `httpx2.MockTransport` with the official `OpenAI` client. This was verified from the selected installed release, not inferred from Anthropic or older SDKs. Both role dependency manifests include `openai` and `httpx2`. SDK retries are forced to zero on bound clients; application retries share the original response budget.

## Selected request profile

The current [model migration guide](https://developers.openai.com/api/docs/guides/latest-model#update-api-and-model-parameters), verified 2026-10-27, supports Responses tools and strict structured output. `tutor_openai` selects Luna with low effort and local `api_profile: current`; the Sol judge and optional `tutor_openai_sol` select low effort with `api_profile: reasoning`. Both profiles default omitted effort to `low` and allow through `max`; only `current` permits `none`. Temperature in 0–2 requires resolved effort `none`, so Sol routes omit it. All selected examples use `service_tier: default` (standard). The profile is local metadata and never enters the SDK body; capabilities are not inferred from a model name. Logical `max_tokens` maps to `max_output_tokens`, including reasoning output.

[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) now uses `prompt_cache_options: {mode: implicit, ttl: 30m}` by default, with optional `12h`. Unknown nested options, explicit-only mode, and legacy retention in current profiles are rejected before client construction. `prompt_cache_key` remains a nonblank string up to 64 characters. The selected models require at least 1,024 visible input tokens for caching, excluding hidden system tokens; byte-based context admission cannot prove that threshold. Policy, skill pack, instructions, tools and preceding input items stay stable across continuation.

Omitted `api_profile` still selects `legacy`: omitted effort resolves to `none`, supported efforts end at `xhigh`, and `prompt_cache_retention` permits `in_memory` or `24h`. Legacy rejects `prompt_cache_options`. Existing legacy SDK regressions and saved artifacts remain compatible; old snapshots are not rewritten. No new commercial price snapshot is introduced.

## Strict schemas and stateless continuation

[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) requires all object properties to be required and forbids additional properties. Canonically optional read-tool arguments are required nullable wire fields. Optional nulls are removed by their canonical declaration before local dispatch; required nulls and false/zero/empty strings remain available to the tool's ordinary validation. Tutor output requires diagnosis, proposals, and proposal target keys as well as message/rung, and feeds the existing semantic parser.

The [Responses reference](https://developers.openai.com/api/reference/python/resources/responses/methods/create) and [stateless continuation guide](https://developers.openai.com/api/docs/guides/migrate-to-responses) document `store=false`, encrypted reasoning continuation, and matched `function_call_output.call_id`. Every request repeats instructions, disables automatic truncation, explicitly includes encrypted reasoning for compatibility, and replays returned output items in original order. The adapter does not use `previous_response_id`, register remote tools, generate reasoning summaries, or deliver intermediate output. Formatting/engine feedback is appended as a developer input item, retaining the original prefix.

Local continuation with `store=false` avoids reliance on hosted response state; it does not override caching or account/provider retention policy. Both adapters currently buffer all output until engine validation, even with SDK streaming. Operation-owned clients are lazy, reused per provider and closed; injected clients remain caller-owned. SDK/package/key checks concern selected roles only, and rejudge selects only the judge.

## Usage and service conditions

The [Responses usage schema](https://developers.openai.com/api/reference/python/resources/responses/methods/create) reports inclusive input and cached subset; output includes reasoning as a subset. Mapper `openai-responses@2` separates uncached input, cache reads, `cache_write_30m`, `cache_write_12h`, and output. Returned `cache_write_tokens_details.ttl_30m_tokens` / `ttl_12h_tokens` establish durations; a requested TTL is never returned usage evidence. Valid duration counters must fit inclusive input and agree with a present aggregate `cache_write_tokens`. Invalid/unknown subsets or categories preserve independently bounded counts and explicit incompleteness; uncertain uncached input is withheld. For known current requests, absent write counters keep uncached input and writes unknown; only returned zero proves zero writes. Legacy usage without current request evidence remains readable. Missing counters are never explicit zero. A complete response with unknown output reserves its full requested output allowance locally, while normalized billing usage remains missing.

The same reference states that returned `service_tier` reflects execution and may differ from the request. The adapter accepts explicit default/flex/priority requests, uses recognized returned conditions with provenance, records mismatches in evidence, and keeps missing/malformed execution conditions unknown. Geography is unknown without endpoint evidence. No model-name-based billing inference is made.

## Offline verification and limits

Tests use the selected official SDK at its real serialization/stream parsing boundary, with no network or production keys. They cover strict tool schemas, nullable optional argument dispatch, final structured output, distinct call IDs, encrypted continuation, engine rejection/correction, refusal/incomplete/error output, retryable API failure, malformed/empty output, partial stream disconnect/EOF, context/output/time/round limits, concurrent history isolation, and usage/condition propagation. Live endpoint/model support remains deliberately untested: paid execution was not authorized.

Task 8 adds exactly two OpenAI probes beside the two Anthropic probes. Each checks only its own key and creates only its own provider client. Explicit `-o addopts='' -m 'live and openai'` is required for OpenAI; provider markers alone cannot override the repository's configured live exclusion. The first probe verifies stable cache-relevant prefix/settings across sequential engine exchanges and requires a positive reported repeat cache read; the second requires an engine-accepted revised-work question with historical submission retained. Private per-run traces stay under ignored `eval/reports/`. **Neither paid probe body has been run.**

The [cache guide](https://developers.openai.com/api/docs/guides/prompt-caching), fetched again 2026-10-27, documents the 1,024-visible-input-token minimum. The probe records this prerequisite and current implicit `30m` settings; actual positive reads establish observed reuse. A zero read fails the prerequisite/read gate with a diagnostic message, and does not by itself establish volatile-prefix leakage. No padding, latency threshold or teaching-quality inference is added.

The documented `30m` write multiplier is 1.25× uncached input and `12h` is 2.5×; aggregate writes are not charged again. Base prices/cache-read rates and applicable billing conditions still require a verified snapshot. Provider-aware costs remain incomplete: the checked-in pricing snapshot contains only Anthropic rates, and missing usage/returned-tier/geography evidence is not zero or an inferred default. V1 artifacts are adapted read-only; new output is v2. `compare --tutor-treatment tutor_dialogue` declares a tutor experiment; optional `--allow-tutor-dependency-changes` cannot waive changes shared with the judge. Both SDKs currently depend on `httpx2`, so a shared transport upgrade changes the evaluator too. See [eval/README.md](../../../eval/README.md) for installation, independent route activation, rejudge and comparison commands.
